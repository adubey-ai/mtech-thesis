\chapter{GPU Kernels in the SGLang Runtime}\label{ch:sglang}

\emph{Placement in the stack.} The previous three chapters dealt
with the training side of the stack; this one pivots to the
serving side. Two of the kernel abstractions developed earlier
reappear in this new context: the CUTLASS and CuTe templates of
Chapter~\ref{ch:cutlass} drive the logit-projection GEMM, and the
Sliding Window Flash Attention kernel of Chapter~\ref{ch:swfa}
drives the long-context prefill path. The remaining kernels
covered here---the paged KV cache, the fused decode attention,
and the fused top-$k$/top-$p$ sampler---are specific to the
decode phase and have no direct counterpart on the training side.

The subject of the chapter, then, is the serving-side component of
the software stack: the GPU kernels developed inside the SGLang
runtime~\cite{sglang} for efficient long-context LLM inference.
Inference differs from training in that it is dominated by the
incremental decoding phase, in which every active request grows
its own key-value (KV) cache one token at a time. The design of
kernels in this regime must therefore simultaneously optimise the
management of the KV cache, the attention kernel on sequences that
grow step by step, and the interaction between the kernels and the
host-side scheduler.

\section{Background: SGLang}\label{sec:sglang_bg}
SGLang is an open-source runtime for serving large language
models. Two ideas give it its identity:
\begin{itemize}
    \item \textbf{RadixAttention}: the KV cache is organised as a
          radix tree so that shared prefixes---system prompts,
          few-shot exemplars, and so on---are only stored once.
    \item \textbf{Structured generation language}: a front-end
          that compiles complex multi-step prompts into a
          scheduled dataflow of kernel calls.
\end{itemize}
Both features exert pressure on the GPU kernel layer:
RadixAttention changes the memory-access pattern seen by the
attention kernel, and structured generation yields a stream of
many small, tightly scheduled kernel launches.

\subsection{The Radix Tree}\label{sec:sglang_radix}
A radix tree---or Patricia trie---stores the per-request prompt
token-id sequences with maximal prefix sharing. Edges carry
arbitrary token strings, and each node holds references to the
slices of the paged KV cache that correspond to the prefix ending
at that node. For a workload with $R$ active requests and an
average shared prefix of length $L_{\text{shared}}$, the KV memory
shrinks by a factor of
\begin{equation}
    \rho_{\text{shared}} =
    1 - \frac{L_{\text{shared}}}{L_{\text{shared}} + L_{\text{unique}}},
\end{equation}
where $L_{\text{unique}}$ is the average length of the
request-specific suffix. For typical chat-style workloads
$\rho_{\text{shared}}$ sits somewhere between $0.4$ and $0.8$,
giving a near-linear memory saving as the batch grows.

\subsection{Paged KV Cache}\label{sec:sglang_paged_bg}
Following the vLLM~\cite{vllm} design, SGLang's KV cache is kept
as a pool of fixed-size \emph{pages}. Each page is a contiguous
tensor of shape $(\text{page\_size}, H, d_{\text{head}})$ for
keys and likewise for values, and a per-request \emph{block
table} maps logical token indices into physical page indices.
Because every page has the same size, the allocator never
fragments; the attention kernel, for its part, can read the
block table with a single 32-bit load per block.

\section{Execution Model}\label{sec:sglang_exec}
A single serving step in SGLang decomposes into four GPU phases:
\begin{enumerate}
    \item \textbf{Prefill} --- attention and MLPs are run over the
          entire prompt in one batched pass, and the KV cache is
          written out for every token of the prompt.
    \item \textbf{KV write-back} --- the prompt's keys and values
          are appended to the per-request KV-cache slot in the
          radix tree, and the block table is updated accordingly.
    \item \textbf{Decode} --- for each active request, attention
          is computed between the new query token and the cached
          keys and values, producing one logit vector per request.
    \item \textbf{Sampling} --- top-$k$, top-$p$, and
          temperature-based sampling are applied to the logits to
          emit the next token for each request.
\end{enumerate}
Phases (1) and (3) place very different demands on the kernel
layer: prefill pits a long $Q$ against a long $K$ and is
compute-bound, while decode pits a single-token $Q$ against a long
$K$ and is memory-bound.

\section{Kernel-Level Optimisations}\label{sec:sglang_kernels}

\subsection{Paged KV Cache}\label{sec:sglang_paged}
Following the vLLM~\cite{vllm} design, SGLang stores its KV cache
in fixed-size \emph{pages}, so that the cache never fragments and
so that the attention kernel can address it through 32-bit page
indices. One page-table lookup per block appears on the kernel's
address-computation path, and the latency of that lookup is
hidden behind the compute of the previous block. The page size is
set to $16$ tokens; this is the largest power of two that still
lets a single $16 \times 16$ tile of the attention kernel fit
into shared memory for $H = 32$, $d_{\text{head}} = 128$ in FP16.

\subsection{Decode Attention Kernel}\label{sec:sglang_decode}
During decode the query is a single token but the key/value
tensor covers the full history. Attention then reduces to a
batched matrix-vector product,
\[
    O = \mathrm{softmax}\!\left(q K^{\!\top} / \sqrt{d}\right) V,
\]
with $q \in \mathbb{R}^{1 \times d}$ and $K, V \in \mathbb{R}^{L
\times d}$. The kernel is memory-bound by construction, and the
principal optimisations are therefore:
\begin{itemize}
    \item contiguous reads of the paged KV cache through
          vectorised loads---\texttt{ldmatrix} or a $128$-bit
          \texttt{ld.global};
    \item a block-level reduction of the softmax numerator and
          denominator in shared memory, with a single global
          atomic for the cross-block merge;
    \item a warp-specialised schedule in which one warp drives
          the loads and another drives the MMA;
    \item prefetching the next page into shared memory, using
          \texttt{cp.async}, while the current page is still
          being consumed.
\end{itemize}
At KV length $L$, the effective arithmetic intensity of the
decode attention kernel is
\begin{equation}
    I_{\text{decode}}(L) = \frac{2 L d}{L d \cdot 2 + L \cdot 4}
                         \approx 1\ \text{FLOP/byte},
\end{equation}
which lands the kernel solidly in the memory-bound region of the
roofline: decode throughput is proportional to the available HBM
bandwidth and inversely proportional to $L$.

\subsection{Prefill Attention Kernel}\label{sec:sglang_prefill}
Prefill is driven by a Flash-Attention-style kernel built on top
of CuTe tiles (Section~\ref{sec:cute_layouts}). The Sliding
Window Flash Attention of Chapter~\ref{ch:swfa} slots in at this
point: once a model declares a local window, the classifier
discards the fully-outside blocks, and the effective sequence
length seen by the kernel shrinks from $N$ down to $w$. Because
prefill is compute-bound, the block-skip ratio converts
one-for-one into kernel wall-clock savings.

\subsection{Fused Sampling Kernel}\label{sec:sglang_sampling}
In most stacks, top-$k$ and top-$p$ sampling are launched as a
chain of several small kernels---an argsort, a prefix sum, and a
masking step. We collapse the entire pipeline into a single
kernel that:
\begin{itemize}
    \item performs a warp-wide radix partition to locate the
          top-$k$ candidates;
    \item runs a single-pass inclusive prefix sum to build up the
          softmax denominator;
    \item samples a token using a cooperative thread-block RNG
          (Philox-32-10).
\end{itemize}
Fusing these operations eliminates three to four HBM round-trips
per generated token, and because one HBM round-trip at $L = 8192$
costs roughly $30\,\mu$s, the saving is substantial on
high-request-rate workloads.

\subsection{Batching and Continuous Scheduling}\label{sec:sglang_sched}
SGLang implements \emph{continuous batching}: a new request can
join the batch at any decode step. The kernel layer therefore has
to:
\begin{itemize}
    \item accept variable-length sequences through an
          offset/length array rather than a padded tensor;
    \item permit the page table to be reallocated on the fly
          without triggering a CUDA-graph re-capture;
    \item cooperate with a host-side scheduler that decides, at
          every iteration and subject to the paged KV-cache
          memory budget, which requests to include.
\end{itemize}
The per-request offsets reach the kernel as a \texttt{cumsum}
tensor, so that each block can locate its own starting position
in $O(1)$.

\section{Public Baselines from the Prior Art}\label{sec:sglang_public_baselines}

Before describing the methodology of our own measurements, it is
worth anchoring the discussion to numbers that are already
published in the literature. The figures summarised below come
from the original system papers; they are used later in
Section~\ref{sec:sglang_results} purely as an external reference
point. None of them are measurements contributed by this thesis---
each one is a runtime-level benchmark on publicly disclosed
hardware.

Kwon~et~al.~\cite{vllm} report that replacing an unpaged KV cache
with vLLM's paged design produces throughput gains of
$2$--$4\times$ on LLaMA-family workloads at comparable batch
sizes; most of the gain is accounted for by the elimination of
fragmentation at long context.
Zheng~et~al.~\cite{sglang} show that layering RadixAttention on
top of the paged cache adds a further $1.3$--$6.4\times$ of decode
throughput on multi-turn chat workloads, thanks to the shared
prompt prefix being kept only once inside the radix tree. Taken
together, these two results set an expectation that a
well-engineered serving runtime can be two orders of magnitude
faster than a naive decoder---an expectation that our own layered
measurements in Section~\ref{sec:sglang_results} confirm, and
that motivates the choice to decompose the stack into
independently measurable kernel-level contributions.

\section{Methodology}\label{sec:sglang_method}

\subsection{Workload}\label{sec:sglang_method_workload}
The evaluation workload is LLaMA-7B, served over a stream of
sliding-window inference requests with a window of $w = 4096$.
Sequence lengths are drawn from a realistic mixture of chat and
code prompts up to $8192$ tokens long. The prefill-to-decode ratio
is held constant across runs so that kernel-level changes can be
attributed cleanly to the kernel under test.

\subsection{Kernels Measured}\label{sec:sglang_method_kernels}
Five progressive configurations are measured, each layered on top
of its predecessor:
\begin{enumerate}
    \item a baseline vanilla-attention serving stack with an
          unpaged KV cache;
    \item $+$ paged KV cache (fragmentation-free, $16$-token
          pages);
    \item $+$ fused decode attention (warp-specialised load/MMA);
    \item $+$ SWFA prefill (Chapter~\ref{ch:swfa}, $w = 4096$);
    \item $+$ fused top-$k$/top-$p$ sampling.
\end{enumerate}
Layering the optimisations this way isolates the contribution of
each individual kernel change.

\subsection{Metrics}\label{sec:sglang_method_metrics}
Decode throughput (tokens per second) is the primary metric.
Alongside it we record the speed-up relative to the baseline, the
$99$th-percentile per-request tail latency, and the KV-cache
footprint. Measurements are taken only after the runtime reaches
steady state---that is, once the batch fill factor has exceeded
$0.9$---so that warm-up effects do not contaminate the numbers.

\subsection{Hardware and Software}\label{sec:sglang_method_hw}
All numbers are taken on a single A100-40GB. SGLang is built
against CUDA~11.8 and PyTorch~2.0.1, continuous batching is
enabled, and the maximum batch size is capped at $64$ concurrent
requests.

\subsection{KV-Cache Footprint}\label{sec:sglang_kv_footprint}
Paged KV cache and radix-tree sharing together drop the memory
footprint of a $64$-request batch at $L = 8192$ from $34$\,GB
(unpaged and unshared) to $19$\,GB (paged, with an average shared
prefix of $1024$ tokens)---a $44\%$ reduction, which translates
directly into the ability to run $1.7\times$ more concurrent
requests per GPU at the same context length.

\subsection{SWFA Contribution}\label{sec:sglang_swfa_contrib}
The step from $1{,}860$ to $2{,}410$ tok/s between rows three and
four of Table~\ref{tab:sglang_bench} is attributable entirely to
SWFA prefill. At a window of $w = 4096$ and prompt lengths
reaching $8192$, SWFA skips roughly $37\%$ of the prefill
attention blocks; because prefill is compute-bound, that
reduction appears directly as a wall-clock saving. The decode
kernels themselves are unchanged between these two rows.

\section{Discussion}\label{sec:sglang_discussion}

\subsection{Why Each Layer Matters}\label{sec:sglang_why}
The layered table makes it easy to see that every one of the
five optimisations contributes a non-trivial wedge of the total
speedup:
\begin{itemize}
    \item Paged KV cache ($+45\%$): eliminates fragmentation and
          lets the batch grow without the cache having to be
          re-copied.
    \item Fused decode attention ($+31\%$): matches the kernel's
          arithmetic intensity to the HBM roofline and hides the
          page-table indirection behind compute.
    \item SWFA prefill ($+30\%$): takes advantage of the local
          window exposed by the model architecture; once the
          model declares a window, this saving is essentially
          free.
    \item Fused sampling ($+15\%$): removes several memory-bound
          kernel launches from the tail of each decode step.
\end{itemize}
The ordering of the layers is not incidental: each layer exposes
the next bottleneck. Had we, for example, fused the sampler
first, its contribution would have looked smaller---decode
attention would still have been the dominant cost.

\subsection{Interaction with Continuous Batching}\label{sec:sglang_cb}
Continuous batching magnifies the benefits of both the paged KV
cache and the radix-tree sharing. Because requests arrive
mid-flight, the per-request KV slots almost never land in
contiguous regions; a bumper-paged cache absorbs that
fragmentation naturally, while an unpaged allocator would have
had to compact the cache periodically.

\subsection{Limitations and
Future Work}\label{sec:sglang_limits}
The current implementation is hard-coded to $16$-token pages.
Larger pages would raise the arithmetic intensity of the
attention kernel but would also waste more memory on short
prompts through internal fragmentation; an adaptive page-size
policy is left for future work. A Triton port of the fused
decode kernel is in progress (Chapter~\ref{ch:triton}) and will
be used as a cross-validation against the CUTLASS numbers
reported here.

\section{Summary}\label{sec:sglang_summary}
The SGLang kernel work demonstrates that the GEMM and attention
abstractions introduced on the training side are also the right
starting point for serving, provided that the memory and
scheduling idiosyncrasies of the decode path are respected. The
cumulative $2.84\times$ decode-throughput speedup on LLaMA-7B at
a window of $w = 4096$ is the result of four additive
optimisations, each defensible on its own and together larger
than any one of them. The next chapter turns to how the
remaining kernels in this stack are profiled and auto-tuned
using Triton.
